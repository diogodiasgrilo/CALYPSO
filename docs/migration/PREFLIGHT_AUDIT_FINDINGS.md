### [1] (critical/logic-error) Progressive-slippage entry retry reuses the SAME cOID for every attempt — IBKR rejects all retries as duplicate orders, defeating the chase-to-fill mechanism

- **Domain:** Order write path + cOID dedup + multi-leg · **File:** `bots/hydra/base_strategy.py` L2314-2439 (coid=external_ref at L2375 and L2397); external_ref source L2079-2141; strategy_id L5023; _ensure_coid shared/ib_client.py L2090-2100
- **Verdict:** confirmed (auditor confidence 0.86)
- **Description:** In _place_option_order_ib the progressive retry loop iterates PROGRESSIVE_RETRY_SEQUENCE and on every attempt calls self._place_leg_order(..., coid=external_ref). external_ref is a STABLE per-leg string (e.g. f"{entry.strategy_id}_LC" at base_strategy.py:2084, where strategy_id = f"hydra_{YYYYMMDD}_entry{entry_num}" at strategy.py:5023). That single string is threaded down as the IBKR cOID for EVERY attempt. IBKR's cOID (Customer Order ID) is documented as 'unique for a 24h span' and is rejected on reuse: ibind 0.1.23's handle_questions explicitly maps 'Order couldn\'t be submitted: Local order ID=' to ExternalBrokerError('Orders are already registered') (.venv/.../ibkr_utils.py:303-305). So: attempt 1 places a LMT at mid, times out (place_and_wait_for_fill leaves it working), is cancelled at L2426-2431; attempt 2 places a DIFFERENT order (higher slippage / MKT) but with the SAME cOID -> IBKR rejects it as already-registered -> _place_leg_order catches the exception (strategy.py:2011-2019) and returns success=False; attempts 3..N likewise. Net effect: only the FIRST attempt can ever reach the market. The entire progressive-chase fill mechanism (the core of HYDRA entry placement) is non-functional on IBKR. The P7 audit only pinned 'cOID identical across retry attempts of the SAME _ib_call' (P7_AUDIT_FINDINGS.md H12 / tests/test_ib_client_reads.py:1446 test_retried_place_uses_same_coid) — correct for network-level retry of one logical order, but the strategy-level retry of genuinely-different orders needs a DISTINCT cOID per attempt. The two requirements directly conflict and the second was never considered.
- **Why it matters:** On a fast-moving 0DTE chain a mid-price limit frequently won\'t fill in 30s; the bot is supposed to climb the slippage ladder to MKT. Here every climb-attempt is dead-on-arrival. Worst case: the opposing long leg filled on attempt 1 of its own placement while the short leg\'s attempt 1 missed and all its retries are duplicate-rejected -> the entry can\'t complete -> naked/partial exposure forced into _unwind_partial_entry. This is a wrong/duplicate-order-class safety failure on the highest-risk path, and it silently degrades to 'no fill' so it may not be caught until a real partial-leg event in production.
- **External evidence:** ibind 0.1.23 ibkr_utils.handle_questions raises ExternalBrokerError('Orders are already registered') on 'Order couldn\'t be submitted: Local order ID=' (.venv/lib/python3.11/site-packages/ibind/client/ibkr_utils.py); IBKR Web API OrderRequest.coid doc 'Customer Order ID, unique for a 24h span' (ibkr_utils.py:492); IBKR Campus Web API cpapi-v1 cOID/clientId uniqueness — https://www.interactivebrokers.com/campus/ibkr-api-page/cpapi-v1/
- **Suggested fix:** Give each distinct placement attempt a distinct, but still deterministic+idempotent, cOID. E.g. derive a per-attempt suffix: coid=f"{external_ref}_a{attempt}" inside the loop (keeps internal _ib_call network-retry idempotency — the same attempt retries with the same cOID — while making each NEW order unique). Alternatively let _ensure_coid append a short uuid per call when the caller passes a base ref intended as a prefix. Add a test that places attempt 1, cancels, then places attempt 2 and asserts the second cOID differs from the first.
- **Verifier reasoning:** I independently traced the full chain and it holds. (1) The progressive-retry loop in _place_option_order_ib passes coid=external_ref on EVERY attempt (base_strategy.py:2375 for MKT, :2397 for LMT) — the loop variable `attempt` is never folded into the cOID. (2) external_ref is a stable per-leg string built once per entry: f"{entry.strategy_id}_LC/_LP/_SC/_SP" (base_strategy.py:2084,2102,2120,2141), and strategy_id is per-entry, not per-attempt. (3) _ensure_coid (ib_client.py:2100) returns `coid or f"CAL_{uuid...}"` — a non-None caller ref is used verbatim and never made per-attempt-unique; the uuid path only triggers when coid is None. (4) That cOID is placed verbatim into OrderRequest.coid (ib_client.py:2329) and submitted to ibind via _submit_order. (5) ibind raises ExternalBrokerError("...Orders are already registered...") on cOID/local-order-id collision (ibkr_utils.py:310-311). (6) IBKR documents cOID as "unique for a 24h span" (ibkr_utils.py:492), and the IBKR Campus Web API docs confirm reuse within 24h — including after a cancel — is rejected as duplicate; the loop's cancel at base_strategy.py:2426-2431 does NOT free the cOID. (7) strategy.py:2011-2019 swallows that exception and returns success=False/filled=False, so attempts 2..5 (including the final guaranteed-fill MARKET escalation) are dead-on-arrival once attempt 1's mid-limit times out — the common 0DTE case. The P7 test test_retried_place_uses_same_coid only guarantees same-cOID for network-retry of ONE logical order, which is the opposite requirement from per-attempt-distinct cOIDs for genuinely different orders; the conflict is real and unhandled. Minor uncertainty: the precise IBKR error string for a cancelled-then-reused cOID isn't proven at runtime and may not match ibind's exact "Local order ID=" branch — but even then IBKR rejects the duplicate per documented 24h uniqueness, so retries still fail to reach the market. Net effect (chase-to-fill non-functional, silent degrade to no-fill, partial/naked exposure risk) is robust regardless. Severity remains critical: this is the highest-risk entry path and the failure is silent.
- **Verifier evidence:** base_strategy.py:2397 `order_type="LMT", limit_price=limit_price, coid=external_ref,` (and :2375 `order_type="MKT", coid=external_ref,`) — same stable ref every loop iteration; external_ref = f"{entry.strategy_id}_LC" (base_strategy.py:2084). ib_client.py:2100 `return coid or f"CAL_{uuid.uuid4().hex[:12]}"` (no per-attempt uniqueness when ref is non-None). ibind ibkr_utils.py:310-311 `if "Order couldn't be submitted: Local order ID=" in data['error']: raise ExternalBrokerError(... Orders are already registered ...)`. ibkr_utils.py:492 `coid (str): Customer Order ID, unique for a 24h span.` IBKR Campus Web API (https://www.interactivebrokers.com/campus/ibkr-api-page/cpapi-v1/): cOID "value must be unique for a 24h span" — reuse within 24h rejected as duplicate.

### [2] (high/security) Unauthenticated path traversal (.md LFI) in agent report endpoints via unvalidated date_str/agent

- **Domain:** Dashboard backend + Google Sheets + Homer journal · **File:** `dashboard/backend/services/agent_reports.py` L53-74 (get_report_for_date); router dashboard/backend/routers/agents.py L19-25
- **Verdict:** confirmed (auditor confidence 0.9)
- **Description:** GET /api/agents/report/{agent}/{date_str} passes date_str unvalidated into agent_reports.get_report_for_date, which interpolates it directly into pathlib glob calls: `agent_dir.glob(f"{date_str}.md")` and `agent_dir.glob(f"{date_str}*.md")` (L59-60). Unlike the hydra (/api/hydra/entries) and metrics routers — which guard date params with `_DATE_RE = ^\d{4}-\d{2}-\d{2}$` — the agents router applies NO validation. I verified on this Python that pathlib glob honors `..` segments: `Path('/intel/apollo').glob('../../secret.md')` resolves to and reads `/secret.md`. So `GET /api/agents/report/apollo/..%2f..%2f..%2f..%2fopt%2fcalypso%2fconfig%2fconfig` (or any path ending up at an existing .md) discloses arbitrary .md files on the host. `agent_name` is also only `.lower()`-ed (L25/L55), not whitelisted against the AGENTS list, so it compounds the traversal of the base directory. This API has no authentication (api_key only gates the WebSocket, and only when set; default is empty) and is exposed publicly on port 8080 (nginx server_name _, CORS allows http://35.231.243.156:8080).
- **Why it matters:** Arbitrary file read on an internet-reachable, unauthenticated endpoint. Even limited to .md files, intel/journal/strategy notes are sensitive; combined with agent_name traversal it can escape the intel directory entirely. On a paper-trading box this is a confidentiality breach, and the same box holds bot config and credentials paths.
- **External evidence:** https://salvatoresecurity.com/preventing-directory-traversal-vulnerabilities-in-python/ and https://www.apisec.ai/blog/path-traversal-in-apis-detection-and-prevention — unvalidated user input in file-path operations is a path-traversal vuln; remediation is resolve()+containment check. Verified locally that pathlib.Path.glob('../../x.md') traverses parents and reads the file.
- **Suggested fix:** Validate `date_str` with the same `^\d{4}-\d{2}-\d{2}$` regex used in hydra.py/metrics.py and reject non-matching input with 400. Whitelist `agent` against AGENTS. Additionally, after building the candidate path, call `.resolve()` and verify it is within `intel_dir.resolve()` (e.g. `intel_dir.resolve() in candidate.resolve().parents`) before reading.
- **Verifier reasoning:** The finding is accurate on every material point. get_report_for_date interpolates user-controlled date_str and agent directly into pathlib glob calls with no validation, while sibling routers (hydra.py, metrics.py) guard date params with ^\d{4}-\d{2}-\d{2}$. I empirically confirmed that pathlib glob honors ../ segments and yields a path outside the base dir that read_text() will then read. The agents router has no auth (only CORS middleware in main.py; no Depends), the api_key gates only the WebSocket handler and only when non-empty (default ""), and nginx proxies /api/ publicly on 8080 with server_name _ and CORS listing the public IP 35.231.243.156:8080. The only refinement: reads are constrained to paths matching {date_str}.md / {date_str}*.md, so it is .md-restricted LFI rather than truly arbitrary file read — but the finding explicitly acknowledges this, and traversal can still escape the intel directory.
